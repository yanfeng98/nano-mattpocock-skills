# 逻辑原型

一个自包含的单个 HTML 文件（一份**可分享的演示**），让任何人靠着点按钮就能驱动一个状态模型。当问题关乎**业务逻辑、状态流转或数据形状**时用它：这类东西在纸上看着合理，只有把它推过真实情形才会感觉不对。

因为它是一个文件、什么都不用安装，你可以把它交给非开发者（设计师、PM、领域专家），让他们亲自感受这个模型。所以它说的是他们的语言，不是代码的语言。

## 什么时候这是对的形状

- 「我不确定这个状态机处不处理得了先 X 后 Y 这种边界情况。」
- 「这个数据模型真的能让我表示出那种情况吗：……」
- 「我想在动手写之前先摸出这个 API 该长什么样。」
- 任何有人想**按按钮、看状态变化**的场合。

如果问题是「这个该长什么样」，那就是走错了分支。用 [UI.md](UI.md)。

## 流程

### 1. 把问题说出来

在写代码之前，写下你正在做原型的是哪个状态模型、哪个问题。一段话，放在演示的顶部（放在看得见的引言里，而不只是一条注释）。回答错问题的逻辑原型是纯粹的浪费，所以把问题写明确，好让它在之后能被核对，无论用户是现在就在看，还是 AFK 回来再看。

### 2. 把逻辑隔离在一个可搬运的模块里

把真正的逻辑（回答问题的那个部分）放进单个 `<script>` 块，写成一个小而纯的模块，好让它之后能被拎出来、丢进真实代码库。它周围的那个页面是用完就扔的；这个模块不是。

对的形状取决于问题：

- **一个纯 reducer**：`(state, action) => state`。当动作是离散事件、状态是单个值时合适。
- **一个状态机**：显式的状态与流转。当「此刻到底哪些动作合法」也是问题的一部分时合适。
- **一小组纯函数**，作用在一个朴素数据类型上。当没有隐含的当前状态、只有变换时合适。
- **一个方法面清晰的类或模块**，当这份逻辑确实拥有持续的内部状态时。

挑最适合所问问题的形状，*而不是*最容易接到页面上的形状。保持它纯净：没有 DOM，没有 `document`，没有按钮处理器伸进它里面。页面调用它；没有东西往反方向流。这正是让原型在自身寿命之后仍然有用的原因：问题一旦答完，验证过的 reducer / 状态机 / 函数集合就能自行拎进真实模块。

### 3. 搭出那个可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：不用框架，不用打包器，不用服务器，所有东西都内联，好让它双击就能打开、在邮件里传来传去也活得下来。任何人都应该能靠打开它把它跑起来。

为一位非开发者来写。每个标签都用**领域语言**，不是代码：按钮与状态读起来像业务，不像 reducer。用大白话解释正在发生什么。

用一套干净的层级从上到下排布：

1. **标题与一行解释**，说明这个演示让你探索什么（第 1 步里的那个问题）。
2. **当前状态**：完整的相关状态，渲染成一块可读的面板（带标签的字段，不是原始 JSON 转储），每次点击后重新渲染，让变化看得见。在有助于非开发者跟上来的地方，点出刚刚变了什么。
3. **自由点按的按钮**：每个动作一个按钮，始终可用，让任何人都能按任意顺序戳这个模型。每次点击派发它的动作并重新渲染状态。
4. **引导式演练**：一组**场景**，每个标签页一个。每个标签页里有一段对场景的简短大白话描述（它铺出的局面，以及要留意什么），下面则是这个场景里按顺序要按的**按钮**。每一步都是真按钮：点它就执行那个动作，并前进到下一步。开始一次演练会重置到一个已知的初始状态，让这个场景每次都以同样的方式跑。

挑选能展示那些别扭情形的场景，也就是在纸上很难推理的那些：顺利路径（happy path）、一例棘手的边界情况、一次试图做本该非法之事的尝试。

保持好看但克制：干净的排版、慷慨的间距、一个强调色。不要动画，不要花招：任何会与状态和按钮抢戏的东西都不要。

### 4. 交出去

把文件发给他们，或者替他们打开。他们什么时候有空就什么时候点过那些演练和自由点按；有意思的时刻是他们说「等等，这不该是可能的」或者「咦，我以为 X 会不一样」的时候；那些是*想法*里的 bug，而这就是全部的意义。如果他们想要新动作或新场景，就加上去。原型会演化。

### 5. 把答案与原型都捕获下来

原型答完它的问题之后，先把答案捕获下来，然后按 [SKILL](SKILL.md) 描述的方式把原型也捕获下来。逻辑特有的映射：验证过的 reducer / 状态机 / 函数集合拎进真实模块（决策被吸收）；HTML 外壳随行到那个把原型留作一手来源（primary source）的用完就扔分支上，而它既然是一个自包含文件，在那里就依然能毫不费力地重跑。

## 反模式

- **不要加测试。** 一个需要测试的原型就不再是原型了。
- **不要把它接到真实数据库上。** 除非问题专门关乎持久化，否则用内存状态。
- **不要泛化。** 不要「要是我们以后想支持 X 呢」。原型只回答一个问题。
- **不要把逻辑与页面混作一团。** 如果这个纯模块引用了 DOM、`document` 或按钮处理器，它就不再能被拎出去。把页面保持为覆盖在一个纯模块上的薄壳。
- **不要伸手去拿框架、打包器或服务器。** 一个收件人双击就能打开的文件；一个 React 应用或一台 dev server 会毁掉「可分享」。
- **不要把 HTML 外壳发到生产环境。** 这个页面是为手动点按而优化的。它背后的逻辑模块才是值得留下的那一部分。
