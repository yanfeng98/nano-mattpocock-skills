# 分诊

让项目问题跟踪器上的 issue 在一台由分诊角色组成的小型状态机里流转。

如果这个仓库把外部 pull request 当作一种请求入口（见 issue-tracker 配置），分诊也要覆盖它们：**一个 PR 就是带代码的 issue**，用的是同一套角色、同一套状态、同一台状态机，只有下面标注 "for a PR" 的几处差异。把光秃秃的 `#42` 解析成 issue 还是 PR，按跟踪器配置来。

分诊期间发到问题跟踪器上的每条评论或 issue，**必须**以这条免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：怎么写耐用的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 这个知识库怎么运作

## 角色

两个**类别**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：等维护者评估
- `needs-info`：在等报告人补充信息
- `ready-for-agent`：已完整说明，可以交给 AFK 的 agent
- `ready-for-human`：需要人来实现
- `wontfix`：不会处理

对 PR 来说，同样的状态要对着随附的代码来读：`ready-for-agent` 意味着已经附上简报，应当由 agent 在这个 diff 上走下一步；`ready-for-human` 意味着可以让人来合并了。

每个分诊过的 issue 都应当恰好带一个类别角色和一个状态角色。如果状态角色互相冲突，先标出来并问维护者，再动别的。

这些是规范角色名。问题跟踪器里实际使用的标签字符串可能不同。映射关系本应已经提供给你。如果没有，让用户运行 `/setup-matt-pocock-skills`。

状态流转：没有标签的 issue 通常先到 `needs-triage`；从那里移向 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告人一回复，`needs-info` 就回到 `needs-triage`。维护者随时可以推翻；看到不寻常的流转就标出来，问过再动。

## 调用方式

维护者调用 `/triage`，用自然语言描述想要什么。理解这个请求并行动。例如：

- 「把需要我处理的东西都列出来」
- 「看看 #42」（issue 或 PR）
- 「把 #42 移到 ready-for-agent」
- 「有哪些可以交给 agent 了？」

## 列出需要处理的东西

查询问题跟踪器，按最旧的在前，列出三组：

1. **未打标签**：从未分诊过。
2. **`needs-triage`**：正在评估。
3. **`needs-info`，且自上一条分诊笔记以来报告人有过活动**：需要重新评估。

PR 在范围内时，把这些组里也纳入外部 PR，并给每行标上 `[PR]` 或 `[issue]`。发现环节只暴露*外部* PR（谁算外部由跟踪器配置定义），所以协作成员手上正在做的 PR 不算分诊工作。这个过滤只在发现环节生效；只要被明确点名，无论作者是谁都要分诊。

显示数量和每项的一行摘要。让维护者来挑。

## 分诊某个具体的 issue 或 PR

1. **收集上下文。** 读完整的 issue 或 PR（正文、评论、标签、作者、日期；PR 还要读 diff）。解析已有的分诊笔记，避免重复问已经解决的问题。用项目的领域术语表来探索代码库，尊重该区域的 ADR。对着代码库跑两项检查：(a) **冗余**：按领域概念（不只是请求的字面措辞）搜索所请求的行为是否已有实现，并报告你查过哪里。如果找到了，就是一个「已经实现」的 `wontfix`（第 5 步）。(b) **先前是否被否过**：读 `.out-of-scope/*.md`，把任何与此请求相似的条目摆出来。

2. **给出建议。** 把你的类别与状态建议连同理由告诉维护者，再附上与该请求相关的简要代码库概要（包括它是否已经实现）。等指示。

3. **核实说法。** 在拷问之前，先确认这个说法站得住。对 bug，按报告人的步骤复现。对 PR，确认这个 diff 确实做到了它声称的事：检出它，跑相关的测试或命令。报告结果：已确认（带上代码路径）、失败，或者细节不足（这是 `needs-info` 的强信号）。核实通过会让 agent 简报强得多。

4. **拷问（如有必要）。** 如果这个请求还需要充实，调用 Skill 工具两次，分别为 "grilling" 和 "domain-modeling"，一轮问题一轮问题地把它拷问成形，磨利领域术语，并在决策落定时就地更新 `CONTEXT.md`/ADR。

5. **落实结果：**
   - `ready-for-agent`：发一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent 简报相同，但要说明为什么它不能被委派出去（需要判断、外部访问、设计决策、手工测试）。
   - `needs-info`：发分诊笔记（模板见下）。
   - 对 `wontfix`，关闭这个 issue，评论内容取决于*为什么*：
     - **已经实现**：改动在代码库里已经存在。指出它在哪；**不要**写进 `.out-of-scope/`（那个知识库是给*被否掉*的请求用的，不是给已经做出来的）。
     - **否掉（bug）**：给出礼貌的解释，然后关闭。
     - **否掉（enhancement）**：写进 `.out-of-scope/`，在评论里链接过去，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：打上这个角色。如果有部分进展，可以选发一条评论。

## 快速改写状态

如果维护者说「把 #42 移到 ready-for-agent」，就信他，直接打上角色。先确认你将要做什么（角色变更、评论、关闭），然后动手。跳过拷问。如果在没有拷问会话的情况下移到 `ready-for-agent`，问一下他们是否要写一份 agent 简报。

## needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- 要点 1
- 要点 2

**What we still need from you (@reporter):**

- 问题 1
- 问题 2
```

把拷问期间定下来的所有东西都归到 "established so far" 下面，免得白做。问题必须具体、可执行，不能是「请提供更多信息」。

## 继续上一次会话

如果 issue 或 PR 上有先前的分诊笔记，读它们，检查报告人是否回答了悬而未决的问题，并在继续之前给出更新后的图景。不要重问已经解决的问题。
